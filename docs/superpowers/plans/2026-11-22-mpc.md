# C5 Constrained Tracking MPC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A 60 Hz MPC ball controller that solves a CFTOC with CasADi + OSQP, keeps the predicted ball inside the planner's corridors, and runs behind the same ROS 2 interface as PID/LQR.

**Architecture:** `mpc/mpc_law.py` holds the CFTOC (built once with `casadi.Opti('conic')`, `opti.to_function`, OSQP) plus the LQR-style observer, delay prediction, warm start and fallback. `mpc/controller.py` reuses `PidPathController`'s run logic and watchdog, and adds route/corridor input and the horizon reference. `mpc/node.py` reuses `PidNode` and subscribes to `/maze/route`.

**Tech Stack:** Python 3.10, numpy 1.21.5, casadi 3.6.7 (OSQP plugin), ROS 2 Humble, pytest.

**Spec:** `docs/superpowers/specs/2026-11-22-mpc-design.md`

## Global Constraints

- `casadi==3.6.7`, pinned in `docker/Containerfile`. Do not upgrade numpy (ROS is built against 1.21).
- QP backend: OSQP only. Warm start goes through CasADi's `warm_start_primal: True, warm_start_dual: True`. Passing OSQP's own `warm_start` raises in CasADi.
- Limits: `max_tilt 0.08 rad` and `max_rate 0.3 rad/s`, the same keys as `lqr.yaml`. They must stay below Contract 4 (`0.087 rad`, `0.5 rad/s`).
- Model: reuse `ball_model` and `c2d` from `maze_control/lqr/lqr_law.py`. Do not copy them.
- No ROS imports in `mpc_law.py` or `controller.py`.
- Commit titles start with `[control]` (or `[docker]` for the Containerfile). No Co-Authored-By or "Generated with" lines.
- Run tests in the container: `cd src/maze_control && distrobox enter maze-sim -- python3 -m pytest test -q` (distrobox keeps the cwd).

## Review Focus

1. **Startup latency.** The first `to_function` call is far slower than later ones (11.6 ms measured vs 3.4 ms median). The constructor does one warm-up solve, so the first real step is not a fallback (test in Task 1).
2. **A replan with the same points but a new `plan_id`.** It must start a new run: stored plan, fallback counter and `stopped` all reset (test in Task 3).
3. **A single-point path** (`point` scenario). The tangent is undefined there, so V = 0, the reference is the point, and there is no NaN (test in Task 3).
4. **A ball already outside its corridor** (noise, or a corridor handover). The slack keeps the QP solvable, and the command still respects the limits (test in Task 1).
5. **A route with `STATUS_NO_PATH` / empty path.** Status is `no_path` and the board goes level, as with PID (test in Task 3).

**Interfaces:**
- Consumes: `ball_model(c, tau, g)`, `c2d(A, B, dt)`, `design_gain(...)` from `maze_control.lqr.lqr_law`.
- Produces:
  - `HorizonRef` (dataclass, `mpc_law.py`): `R, V, lo, hi: np.ndarray`, each of shape `(2, N)`. `lo`/`hi` may be `±np.inf`, which means unconstrained.
  - `class CFTOC(Ad, Bd, dt, horizon, q_pos, q_vel, r, r_du, rho_lin, rho_quad, max_tilt, max_rate, osqp_opts: dict)`. `Ad`/`Bd` are the 3-state single-axis model, and the class builds the block-diagonal 6-state model itself.
  - `CFTOC.solve(x0: (6,), ref: HorizonRef, u_prev: (2,)) -> Plan`, with `Plan(U: (2,N), X: (6,N+1), S: (2,N), ok: bool, t_solve: float)`. State order: `[px, vx, θx, py, vy, θy]`.
  - `CFTOC._solve_qp(args: list) -> (outputs: list, ok: bool)`, the single hook that calls the CasADi function. Tests monkeypatch it to inject failures.

### Task 2: MPCController: observer, delay prediction, warm start, fallback

**Files:**
- Modify: `src/maze_control/maze_control/mpc/mpc_law.py`
- Test: `src/maze_control/test/test_mpc.py`

**Interfaces:**
- Consumes: `CFTOC`, `HorizonRef` and `Plan` from Task 1.
- Produces: `class MPCController` with
  - `from_params(model: dict, mpc: dict, limits: dict, rate_hz: float, g=G) -> MPCController`. Keys: `model{c,tau,delay}`, and `mpc{horizon,q_pos,q_vel,r,r_du,rho_lin,rho_quad,solve_budget,max_fallback,osqp{...}}`.
  - `step(ref: HorizonRef, pos, vel, dt) -> np.ndarray(2)`.
  - `step_zero(dt) -> np.ndarray(2)`.
  - `reset()`, which clears the stored plan and the fallback counter.
  - Attributes `n_delay: int`, `mode: str` (`'ok' | 'fallback' | 'level'`), `n_fail: int` and `last_plan: Plan | None`.

- [ ] **Step 1: Write the failing tests.**
  - `test_step_output_is_limited_and_tracked_by_observer`: 30 steps toward a far reference. Every output satisfies the limits (same check as `test_lqr.check_limits`). The observer's `theta` follows the lag of the applied outputs, the same recursion as `LQRController._advance`.
  - `test_delay_prediction_uses_commands_in_flight`: with `delay=0.05` (`n_delay = 3`), after 3 non-zero commands the `x0` given to `CFTOC.solve` equals `Ad`-propagating `[e, v, θ]` through the 3 pending commands. Capture it by wrapping `ctrl.cftoc.solve`.
  - `test_failure_applies_shifted_plan_then_levels`: monkeypatch `ctrl.cftoc._solve_qp` to return `ok=False` after one good solve. Step j (1 ≤ j ≤ `max_fallback`) returns the rate-limited `last_plan.U[:, j]` with `mode == 'fallback'`. Step `max_fallback + 1` gives `mode == 'level'` and an output moving to 0 at ≤ `max_rate·dt`.
  - `test_slow_solve_counts_as_failure`: patch `_solve_qp` to sleep `solve_budget + 5 ms`, so `mode == 'fallback'`.
  - `test_reset_clears_plan_and_failures`: after a fallback, `reset()` gives `n_fail == 0` and `last_plan is None`. The next failure then levels (there is no stored plan).

- [ ] **Step 2: Run the tests and see them fail.** Run `distrobox enter maze-sim -- python3 -m pytest test/test_mpc.py -q -k "step or delay or failure or slow or reset"`. Expected: AttributeError / ImportError on `MPCController`.

- [ ] **Step 3: Implement `MPCController` in `mpc_law.py`.**
  - Observer, the `_pending` deque, `_limit` and `_advance`: reuse the `LQRController` logic for a 2-axis `theta`. Factor the shared parts into a small base class in `lqr_law.py` only if it stays readable. Otherwise duplicate these ~20 lines with a comment pointing at `LQRController`.
  - `step`: the MPC uses **absolute** positions (the reference `R` carries the target), not errors as in the LQR: `x0 = [px, vx, θx, py, vy, θy]` predicted through `_pending`. Then solve. If `ok` and `t_solve ≤ solve_budget`, apply `U[:, 0]` through `_limit` and store the plan (`n_fail = 0`, `mode = 'ok'`). Otherwise use the fallback rules from the spec.
  - If `pos`/`vel` contain NaN, count the step as a failure without calling the solver.
